Revisión técnica · Repositorio

back-marketplace

Backend REST de un e-commerce desarrollado para el TPO de Aplicaciones Interactivas (UADE). Registro y autenticación de usuarios, publicación de productos con imágenes y categorías, catálogo filtrado y paginado, carrito de compras y orden con precio congelado.

repo github.com/Nico1887/back-marketplace HEAD 2bfa9f3 · PR #10 revisión 2026-09-17

01 · Overview

Qué es y qué hace

API REST construida con Spring Boot que modela un marketplace: usuarios que publican productos, compradores que navegan un catálogo y gestionan un carrito, y un checkout que valida stock, lo descuenta y genera una orden de compra con el detalle y el precio unitario congelado al momento de la operación. No incluye pasarela de pagos.

El proyecto arranca con perfil dev (H2 en memoria, se recrea en cada arranque y se carga con datos de prueba desde data.sql). Todas las rutas cuelgan de /api por server.servlet.context-path.

02 · Stack

Tecnologías

Java 17 Spring Boot 4.1.1 Spring Data JPA / Hibernate H2 (dev) · MySQL (prod) Maven + wrapper Lombok Jakarta Bean Validation springdoc-openapi (Swagger) spring-security-crypto (BCrypt)

Usa spring-security-crypto solo para el encoder BCrypt — no Spring Security completo. No hay filtros de autorización protegiendo endpoints.

03 · Arquitectura

Capas en 5 niveles

Arquitectura clásica en capas. Los controllers nunca exponen entidades JPA: siempre trabajan contra DTOs de request/response.

config/Configuración transversal — CORS, OpenAPI/Swagger
controllers/Exposición HTTP (@RestController)
service/Lógica de negocio (@Service, @Transactional)
repository/Acceso a datos (JpaRepository)
entity/Modelo de dominio JPA (@Entity)
dto/Request y response objects (separados en subpaquetes)
exceptions/Excepciones propias + @RestControllerAdvice global

05 · Módulos funcionales

Seis dominios

1 · Auth

completo

AuthController + AuthService. Registro valida email/username únicos (sino 409), hashea password con BCrypt, asigna ROLE_USER. Login verifica hash con matches(), credenciales inválidas → 401.

POST/auth/register POST/auth/login

No emite JWT/token: el login solo valida y devuelve el usuario.

2 · Usuarios

mínimo

UsuarioController + UsuarioService. Casi un placeholder.

GET/usuarios/{id}

3 · Productos (vendedor)

completo

ProductoController + ProductoService. Alta, modificación, baja lógica, gestión de stock, alta/baja de imágenes.

POST/productos PUT/productos/{id} DELETE/productos/{id} (baja lógica) PATCH/productos/{id}/stock?cantidad= POST/productos/{id}/imagenes DELETE/productos/{id}/imagenes/{imagenId}

4 · Catálogo (comprador)

bug path

CatalogoController + servicios. Listado paginado, filtrado por nombre (LIKE) y categoría, ordenado alfabéticamente. Query JPQL con EXISTS sobre categorías.

GET/api/productos?nombre=&categoriaId=&page=&size= GET/api/productos/{id} GET/api/categorias

@RequestMapping("/api") duplica el context-path → rutas reales /api/api/productos. Mismo bug ya fixeado en ProductoController.

5 · Carrito

completo

CarritoController + CarritoService. Agregar ítem validando stock (suma a cantidad existente, verifica hayStock(), si no → 409). Reutiliza detalle existente en vez de duplicar; orphanRemoval correcto.

GET/carrito/usuarios/{usuarioId} POST/carrito/usuarios/{usuarioId}/items PUT/carrito/usuarios/{usuarioId}/items/{productoId} DELETE/carrito/usuarios/{usuarioId}/items/{productoId} DELETE/carrito/usuarios/{usuarioId}/items

6 · Órdenes / Checkout

sin implementar

Existen OrdenCompra, DetalleOrden, OrdenCompraRepository, DetalleOrdenRepository — pero no hay controller ni service. El checkout descripto en el README no está implementado todavía.

08 · Puntos débiles

Deuda técnica detectada

  1. Checkout sin implementar. Existen entidades y repos de orden pero no hay controller ni service. El README promete un checkout que no existe.
  2. Doble /api en CatalogoController. @RequestMapping("/api") + context-path → rutas /api/api/productos. Mismo bug ya fixeado en ProductoController.
  3. ProductoService usa RuntimeException. Los "no encontrado" caen en el handler genérico → 500 en lugar de 404. Inconsistencia con el resto del proyecto.
  4. Sin autenticación real. El login valida credenciales pero no genera token ni hay filtros de seguridad. Los endpoints de vendedor (alta/baja/stock de producto) quedan abiertos.
  5. Usuario inferido por path. /carrito/usuarios/{usuarioId} en vez de inferirlo del usuario autenticado.
  6. Archivos duplicados con typo. CorsConfig.Java y OpenApiConfing.Java (extensión .Java mal) junto a los .java correctos en config/.
  7. Cobertura de tests muy baja. Solo 3 tests de servicio + context loads; sin tests de controller ni integración.
